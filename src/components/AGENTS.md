- Return receipts use persisted return details and actual applied credit; shareable thermal-width PDFs and the existing Telegram message sender avoid confusing returns with sale receipts or promising unsupported direct Bluetooth printing.
- Client location editing uses ClienteUbicacion with validated decimal coordinates and a lazy Google Maps picker; reuse the existing SDK script/callback to avoid loading Maps twice.
- QuickSale is exclusively a route-sale tool: require an active matching load and validate onboard availability before confirmation and submission; always send its non-null carga_id online and offline to prevent warehouse fallback.
- Reuse CancelarPedido in Preventa and EntregarPedido so reason capture, pending-only updates and immediate truck refresh stay consistent.
- Route finishing uses EstadoRuta: vendors move a load to pendiente_liquidacion via finalizar_ruta_carga (blocks sales/edits, liquidation still allowed) and only admins reopen via reabrir_ruta_carga with an audited reason — separates end of street work from physical truck settlement.
- Route workflow is split into Iniciar ruta (only en_ruta loads; otherwise a 'No hay rutas pendientes' state), Carga de camión (load creation and trucks on route) and Liquidación de ruta (pendiente_liquidacion and closed loads), sharing CargaCamionPage by modo — keeps street sales from ever using finished or closed routes.
- Payment form (medio_pago catalog), reference and receipt photo are stored separately from the contado/credito condition; sale payment data is saved via registrar_pago_venta after registrarVenta (online and offline), receipts use the evidencias outbox, and in-visit abonos only target the truck route's credits — keeps credit math untouched and offline-safe.
